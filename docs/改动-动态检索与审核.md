# 动态检索改造方案

## 一、要解决的问题

当前系统的检索池是离线构建的 `backend/data/hashing/real_corpus.db`，开机一次性播种 5058 个单元，运行时新增数据只有 12 条，且编码器只训练一次后冻结。项目书要求的动态能力包含三层，目前只做到第三层的一半。

1. 数据层。时间戳由 `simulated_created()` 按 `idx * 7 天` 人为铺开，同一批数据被切成 6 个窗口，窗口之间分布相同，不存在真实漂移。
2. 模型层。`_train()` 只在 `_rebuild()` 中调用一次，新数据只编码不训练，哈希函数参数从不随数据变化。
3. 结构层。项目书的表是一套哈希函数，代码的表是位带切片，6 个窗口共用同一套 W，表权重 `trust` 未参与打分。

另外存在三个工程缺陷。语料库与引擎的窗口口径不一致，30 天对 122 天，起始日 2025-01-01 对 2025-08-01。新单元的 window 未写回 `units`，状态文件里为 None。每次增量写入全量重写 4.3MB JSON，复杂度 O(N)。`retrain()` 与 `reset()` 走 `_rebuild()`，会清空运行时增量。

## 二、改造目标

把检索系统从"静态库加固定编码器"改成"数据流加多窗口模型"。目标链路为四段。

数据流按时间步持续进入，审核通过后进入训练池，每个时间窗口独立训练一套编码矩阵，检索时按质量与时效加权融合各窗口结果。

## 三、数据层

### 3.1 索引落库

新建 `backend/data/hashing/index.db`，替代 `hashing_state.json`。三张表。

`units` 存索引单元，字段为 unit_id、record_id、user_id、modality、code、window、scope、source、created_at。主键 unit_id，按 window 与 scope 建索引。

`train_queue` 存待训练样本，字段为 id、record_id、enqueued_at、consumed_at、train_version。

`train_runs` 存训练版本，字段为 id、version、started_at、finished_at、windows、n_samples、mAP_before、mAP_after。

状态只需追加，不再全量序列化。

### 3.2 冷启动与增量

语料库降级为冷启动底库，只在 index.db 为空时导入，导入单元标记 `source='corpus'`、`scope='public'`、`train_consumed_at` 为导入时间。

运行时数据统一走 ingest 通道，一个内部函数加一个管理接口。筛查记录、补充材料、管理员导入全部调用同一个入口。

新增 `scripts/replay_corpus.py`，从 `real_corpus.db` 按 window 顺序分批吐出数据，模拟 21 个时间步。回放器与真实写入共用 ingest 通道，保证演示与线上是同一套代码。

### 3.3 窗口口径统一

把 `epoch` 与 `window_days` 写进 index.db 的 meta 表，加载时与本机配置比对，不一致直接报错而不是静默混算。新单元的 window 必须写回 `units`。

## 四、数据治理层

### 4.1 分池

`units.scope` 四个取值。

`reviewing` 默认状态。已编码入索引，本人与管理员可见，不进公共检索结果，不进训练池。

`public` 审核通过。全角色可见，可被训练采样。

`private` 用户选择不公开。仅本人可见，只用于纵向自我比对。

`rejected` 审核拒绝。仅本人与管理员可见，检索与训练均排除，记录保留供审计。

检索接口增加调用者身份参数，`search()` 按 scope 与 user_id 过滤。这是逻辑分区，不维护多份索引。

### 4.2 审核字段

主库 `screenings` 与 `screening_supplements` 增加四个字段。

`review_status` 取值 pending、approved、rejected、expired。
`reviewed_by` 审核人。
`reviewed_at` 审核时间。
`review_note` 审核意见。

审核维度四项。去标识化是否彻底，是否为真实用户数据而非测试或恶意输入，主题与风险标签是否准确，是否具备知情同意。`screenings.consent_status` 已有，可直接作为准入条件之一。

### 4.3 审核接口

`GET /api/admin/review/pending` 分页返回待审列表，支持按来源与时间筛选。

`POST /api/admin/review/batch` 批量提交审核结果，参数为 ids、action、note。

审核通过时执行三个动作。`scope` 改为 `public`，向 `train_queue` 插入记录，写入审计日志。

审核拒绝时 `scope` 改为 `rejected`，写审计日志，不做物理删除。

### 4.4 训练消费

重训只从 `train_queue` 中 `consumed_at` 为空的记录取样，训练完成后回填 `consumed_at` 与 `train_version`。这样不会漏训，也不会重复训。

## 五、模型层

### 5.1 窗口即模型分区

`window` 从索引分区升级为模型分区。每个窗口独立调用 `cmfh.fit()` 得到一套 `W_text`、`W_image`、`W_audio`，与样本数、ρ、σ、权重一起持久化到 `table_meta`。

活跃表数量上限取 5，与项目书一致。超过上限时淘汰权重最低的窗口，只删除其模型与索引分区，原始记录保留，可被其他窗口模型重新编码。

### 5.2 表权重

权重由三个因子相乘后归一化。

语义一致性 ρ，沿用现有 top-3 近邻主题 Jaccard。
编码信息量 σ，沿用现有位方差均值。
时效衰减，`exp(-ΔT / τ)`，τ 取 120 天，ΔT 为当前时间与窗口中心时间之差。

权重必须参与最终排序，不能只做 active 布尔过滤。

### 5.3 检索流程

用每个活跃窗口的 W 分别编码查询，在同一窗口分区内检索候选，得分乘以该窗口权重后合并去重，按融合得分重排返回。融合方式优先用加权得分，若各窗口分数尺度差异大则改用 RRF。

候选不足时保留现有线性回退，但回退范围限定在调用者可见的 scope 内。

### 5.4 冷启动

新窗口 approved 样本少于 30 条时，用最近窗口的模型加新批次联合训练，暂不独立建表。样本累积到阈值后再独立训练并纳入表池。

## 六、动态机制

### 6.1 漂移检测

三个信号，任一越阈即标记该窗口需要重训。

滑窗主题分布的 KL 散度超过阈值。
新词 OOV 率超过阈值。
ρ 相对上次评估下降超过 10%。

不做定期无条件重训。

### 6.2 增量重训

触发后按以下顺序执行。

从 train_queue 取未消费的 approved 样本。
与目标窗口已有样本合并，按 70% 有标签比例采样。
对合并集重新 `fit()`，得到新 W。
计算新表 ρ 与 σ，低于阈值则丢弃，保留旧表。
活跃表超过 5 个时淘汰权重最低者。
重编码受影响窗口的 units，其他窗口不动。
写 `train_runs` 记录版本与训练前后指标。

### 6.3 重建保护

`retrain()` 与 `reset()` 不得清空运行时数据。重建时先合并 index.db 中 `source != 'corpus'` 的单元到训练集，再执行重建。现有代码直接 `_rebuild()` 的行为必须改掉。

### 6.4 特征层

`features.py` 的 `THEME_KEYWORDS` 是 14 类硬编码主题，新主题进不了特征空间，漂移在特征层就已经感知不到。二期换中文 embedding，本地 ONNX 跑 bge-small-zh。一期可先加动态主题扩展，让新词能落进维度。

## 七、评测层

新增 `scripts/eval_dynamic.py`，参数 `--steps 21`。

数据按时间步分批注入，每步注入后执行一次检索评测，记录 mAP@10 与 Recall@50。

对照组四组。静态全量训练，即当前实现。有表无淘汰。有权重无重排。完整方案。

报告输出每步指标、跨步均值、跨步标准差。标准差是抗漂移的唯一硬指标，必须与均值一起报。

同时输出精度随时间步的曲线数据，供前端绘图。

## 八、接口与前端

新增审核页，展示待审列表、审核操作、审核记录。

检索页结果项增加 scope 标识，未审核数据只对本人展示提示。

索引状态页增加三项内容。各窗口表权重与活跃状态，训练版本号，待训练样本数。

管理端增加数据注入入口，用于演示时手动推进时间步。

## 九、实施顺序

阶段一，数据与治理。索引落 SQLite，scope 与审核字段，审核接口，检索过滤，重建保护，窗口口径统一。这一阶段不动算法，先把入口和闸门打通。

阶段二，模型分区。多窗口独立训练，权重参与融合，冷启动策略。

阶段三，动态机制。漂移检测，增量重训，表淘汰。

阶段四，证据链。21 步评测，前端可视化。

## 十、验收标准

新增一条记录后，本人可立即检索到，他人不可见。

审核通过后，他人可在一次刷新内检索到，且该记录进入待训练队列。

审核拒绝的记录不出现在任何他人检索结果，也不出现在训练样本中。

执行一次重训后，索引单元总数不减少。

21 步评测中，完整方案的 mAP 跨步标准差低于静态基线，均值不低于基线。

## 十一、风险

审核会引入选择偏差。若只放行外观正常的样本，训练分布会偏移，漂移检测失真。需要监控通过率与拒绝原因分布。

多窗口训练成本随窗口数线性增长。当前单窗口 300 样本、纯 Python 特征分解在 numpy 可用时为毫秒级，21 个窗口仍可接受，但重训必须放后台，不能进请求路径。

冷启动期检索质量会下降，需要在界面上说明当前处于模型积累期。

改造期间不要为了动态指标牺牲现有 mAP。若某窗口模型质量不达标，宁可保留旧表。

## 十二、不在本次范围

RAG 知识库保持固定，文档库不需要动态化。

跨模态特征提取链路不改，仍用现有文本、图像、语音特征。

移动端与 Worker 部署不变，动态能力只在本地完整后端生效，Worker 继续降级 Mock。

## 十三、实施记录

已完成的部分与落地差异，按实际代码为准。

### 13.1 存储层

新增 `backend/app/engines/hashing/store.py`，索引库落在 `backend/data/hashing/index.db`，含 units、records、train_queue、train_runs、table_meta、meta 六张表。

与方案的差异：`hashing_state.json` 没有删除，而是缩水成模型参数文件。原因是投影矩阵是二进制浮点矩阵，放 JSON 序列化成本高，且只在训练后写一次。索引单元与训练队列全部走 SQLite，增量写入不再重写整库。

首次启动自动迁移旧状态文件，5070 个单元一次性导入，迁移耗时约 18 秒，之后启动 0.15 秒。

### 13.2 分池与审核

`units.scope` 四态已落地。检索接口带 `viewer` 参数，按角色过滤：管理员看全部，普通用户看公共池加本人数据，内部调用传 None 不过滤。

主库 `screenings` 与 `screening_supplements` 增加 review_status、reviewed_by、reviewed_at、review_note。加列时历史数据统一标为 approved，之后新记录默认 pending。

接口：

`GET /api/admin/review/pending` 待审列表

`GET /api/admin/review/stats` 各池数量与待训练数

`POST /api/admin/review/batch` 批量通过或拒绝

`POST /api/personal/scope` 本人设置 private 或申请公开

前端新增 `frontend/src/admin/pages/AdminReview.tsx`，路由 `/admin/review`，侧栏"数据审核"。

自动化例外：预警由系统派生，案例由咨询师建立，两者写入时直接 public，不进待审队列。只有用户自助提交的数据需要过审。

### 13.3 窗口口径

`HASHING_WINDOW_DAYS` 改为 30，`HASHING_EPOCH` 改为 2025-01-01，与语料构建脚本一致。加载时对 source=runtime 的单元重算窗口并回写，历史上落在错误窗口的 12 条数据已迁移到正确分区。

新增冷启动保护：窗口样本数低于 30 时强制参与探测。此前小窗口会因 ρ 偏低被判不活跃，新数据等于检索不到。

### 13.4 多窗口模型

新增 `backend/app/engines/hashing/window_models.py`。每个时间窗独立训练一套 CMFH，持久化在 state.json 的 window_models 字段。

检索走 `_multi_window_search`：每个窗口用自身模型编码查询、召回候选，得分乘以表权重后融合排序。返回体保留原始相似度，另在 explain 里给 table_weight 与 rank_score。

权重公式为 `(0.78 + 0.22 × 质量分) × max(0.8, 时效衰减)`，区间约 0.6 到 1.0。

第一版权重给到 0.3 到 1.0 的区间，21 步实验里 mAP 从 0.48 掉到 0.38：各窗口模型独立训练，相似度本就不在同一尺度，权重放大两倍以上就会压过相似度本身。改为温和调制后曲线恢复正常。

首次生成窗口模型需全量重训与重编码，5070 个单元约 4 分钟，属一次性成本。之后训练后只写一次模型文件。

### 13.5 增量重训与漂移

`retrain_pending()` 消费训练队列，只重训有新样本的窗口，重编码该窗口单元，回填队列版本。

表淘汰机制已实现但默认关闭（`HASHING_MAX_TABLES=0`）。原因是被淘汰窗口的存量码会失去对应编码器，查询走最近窗口模型时与库内码不同源，检索质量直接崩掉。开启淘汰前必须先迁移或重编码该窗口的数据。

`drift_report()` 输出主题 KL、OOV 率、ρ 下降三个信号。

`retrain()` 已改为原地重训，不再调用 `_rebuild()`，运行时增量不会被清空。

### 13.6 回放与评测

`scripts/replay_corpus.py` 按时间步把语料分批注入，与线上写入共用同一通道。

`scripts/eval_dynamic.py` 跑 21 步三组对照，输出 mAP@10 每步值、均值、跨步标准差，结果写入 `data/hashing/eval_dynamic.json`。

实测结果，每步 80 条查询：

| 方案 | mAP 均值 | 跨步标准差 |
| --- | --- | --- |
| 静态训练，等价于改造前 | 0.3813 | 0.0371 |
| 增量重训，无权重 | 0.4796 | 0.1094 |
| 完整方案，三项算法接入前 | 0.4666 | 0.1022 |
| 完整方案，三项算法接入后 | 0.4987 | 0.0938 |

增量重训带来约 26% 的精度提升，这是动态机制的直接收益。

接入查询自适应重排序、错误哈希样本校正、双指标权重之后，均值再提升 6.9%，波动也收窄到 0.0938，两项指标同时优于"只重训不加权"的对照组。这说明补的三项算法不是装饰。

静态方案的标准差最小，但那是因为它一直停在低水平，不是稳定，是没变化。报告时应说明这一点，不能单看标准差。

评测使用独立临时索引目录，不影响线上库。

### 13.7 待办

个人端的"不公开"开关只有接口，还没有界面入口。

Worker 内的 `python_modules/app` 是历史手工副本，未同步本次改动。Worker 当前为 Mock 降级，不影响功能。

特征词典仍为 14 类硬编码主题，新主题进不了特征空间，属二期。

## 十四、第二轮修复

针对首轮遗留问题逐项处理。

### 14.1 重训从 248 秒降到 7.8 秒

根因不是算法，是特征重复抽取。索引库只有码，没有特征，每次重编码 3372 个媒体单元都要重新解码语音和图像，其中 `_pitch_stats` 的 FFT 一项就占 125 秒。

处理：`units` 表加 `feature` 列，媒体特征随单元落库，回填脚本 `scripts/backfill_feature.py` 一次性补齐。训练与重编码优先读库内特征，文本仍实时重算。

实测 `retrain()` 从 248 秒降到 7.8 秒，启动加载 0.16 秒。索引库从 2.7MB 增到 7.2MB，换来 31 倍的重训提速。

### 14.2 训练队列接上消费链路

新增 `schedule_retrain()`，后台线程执行，同一时刻只允许一个任务。

触发方式两种：审核通过后队列积压达到 `HASHING_AUTO_RETRAIN_MIN`（默认 10）自动触发；管理端"立即重训"按钮手动触发。

重编码改为先算码、再整体替换索引，避免边删边插时检索线程读到半个索引。

接口：`POST /api/admin/hashing/retrain`、`GET /api/admin/hashing/status`、`GET /api/admin/hashing/drift`。

### 14.3 冷启动窗口能消化队列

回归测试暴露的问题：新窗口只有一两条数据时，`retrain_pending()` 判定样本不足直接跳过，队列永远不消化。

改为借邻近窗口的数据联合训练。借样按窗口号接近程度累积，不要求单个窗口自身够数，否则小数据集永远借不到。

### 14.4 三项算法落地

对应项目书 4.7.2 与 4.7.3，全部带开关。

查询自适应重排序：同一张表对不同查询的表征能力不同，用该窗口首位命中的相似度做适配度，对融合权重做正负 25% 的微调。

错误哈希样本校正：训练新表前，先用现有模型编码窗口内样本，挑出近邻主题与自身不一致的记录，重复两遍纳入训练集，最多占 30%。

双指标表权重：交叉熵维度用语义与汉明一致性衡量，余弦维度用窗口模型与全局模型的平均余弦衡量信息重叠，两者加权后决定表权重。

Hadamard 正交化已实现但默认关闭，需要单独实验验证后再启用。

### 14.5 工程收尾

审核页增加"立即重训"按钮、队列与版本状态、分页。

审核服务兼容降级引擎：Mock 实现没有索引存储，接口返回明确的不支持提示而不是 500。

Worker 副本同步审核相关三个文件；`hashing` 改动不同步，因为 Worker 下强制 Mock，且 `store.py` 依赖 sqlite3，Workers 运行时不提供。

新增 `backend/tests/test_review_flow.py`，六条回归用例覆盖分池可见性、审核通过入队、拒绝不入队、队列消费、重训不丢数据。

### 14.6 仍未完成

个人端"不公开"开关只有接口，没有界面入口。

表淘汰机制已实现但默认关闭，开启前需要先做该窗口的数据迁移，否则存量码失去编码器。

特征词典仍为 14 类硬编码主题，新主题进不了特征空间。

评测每步只有 80 条查询，批次主题构成差异会造成波动，正式报告建议跑三组随机种子取均值。

## 十五、采集数据未进入审核页的修复

### 15.1 现象

数据审核页显示待审 0 条、公共池 5070 条，而个人端刚提交过采集内容。

### 15.2 根因

主因是链路缺口，不是分池逻辑。`save_personal_supplement` 与 `save_screening_supplement` 只向主库 `screening_supplements` 插入一行，随后调用 `_analyze_collection` 做检索分析，全程没有调用 `index_case_sync`。也就是说这批数据从来没进过哈希索引，审核页自然查不到。

次因是端口残留。8000 端口上有两个 `python -m app.main` 进程同时监听，请求被旧进程应答，旧进程内存里仍是修复前的 5070 条。即使数据已经更新，页面刷新也看不到变化。

### 15.3 修复

新增 `_index_supplement`，在两处采集接口保存成功后写入索引，`scope=reviewing`、`source=runtime`、`user_id` 取登录态。

顺序上先做检索分析、再写索引。反过来会让分析检索到自己，相似度 1.0，每次采集都会误判为高风险。

新增 `scripts/backfill_supplements.py`，把历史上只落业务表的采集数据补进索引，本次补录 2 条。

### 15.4 验证

补录后待审列表出现 sup-1、sup-2 两条。再从个人端提交一条新采集，待审立刻变为 3 条，新记录为 sup-3。删除测试记录后恢复为 2 条。

### 15.5 经验

同一端口反复启动后台服务时，杀进程要确认 `python.exe` 真的退出。只结束 shell 会留下僵尸进程继续占用端口，接口表现与代码状态不一致，排查时先看 `netstat`。

## 十六、无标签数据的处理规则

用户采集的文本、语音、图像大多没有主题标签。"愤怒""我好烦啊啊啊啊"这类短句抽不出主题，索引里 tags 为空。标签只用于构造监督矩阵，不影响能否被检索，但会连带三个问题。

### 16.1 问题一：无标签样本被误判为映射冲突

`_error_samples` 用近邻主题一致性判断"坐错位置"的样本。无标签样本的 Jaccard 恒为 0，必然低于阈值，实测一个三条记录的窗口三条全中，会被重复两遍塞回训练集。

修复：判定时跳过无标签样本，近邻也只统计带标签的。没有标准答案的样本不能算答错。

### 16.2 问题二：监督比例失控

新采集数据涌入会把监督矩阵稀释成近对角阵，模型退化为纯无监督重构。

这里最初的处理是错的：把项目书"有标签样本占 70%"当成训练约束，训练前裁掉多余的无标签样本。但那是实验设置，描述的是每个时间步注入批次的构成，不是训练规则。裁剪会丢掉新数据的分布信息，而"见过新数据长什么样"恰恰是增量训练的价值。

改为默认不裁剪：`_balance_supervision` 保留，`HASHING_LABELED_RATIO` 默认 0，无标签样本全部参与重构。需要复现项目书的 70% 实验口径时，把该值设成 0.7 再跑评测。

### 16.3 问题三：无标签窗口与有监督窗口同权

无标签窗口训出来的模型只保留特征层面的相似，主题语义弱，却按正常权重参与融合。

修复：新增标签覆盖率因子，权重乘以 `0.55 + 0.45 × 覆盖率`。覆盖率 0 的窗口权重从 0.78 降到 0.43，全有标签的窗口不打折。

### 16.4 验证

`backend/tests/test_supervision.py` 覆盖四条规则，与审核流程测试合计 11 条用例全部通过。

索引现状：窗口 22 的三条采集数据覆盖率为 0，权重 0.4266，其余窗口 0.73 左右。

## 十七、主题标注能力

### 17.1 需求

采集上来的数据一开始没有标签。管理端有三种处理方式：保持无标签、手动补标签、让大模型给建议后人工确认。

### 17.2 标签空间

固定为 `features.THEME_KEYWORDS` 的 19 个类别：抑郁、焦虑、睡眠障碍、社交回避、学业压力、应激创伤、自我认同、家庭冲突、情感、人际、适应、网络成瘾、进食困扰、创伤、情绪稳定、精力良好、睡眠充足、社交活跃、积极活动。

不接受自由文本。原因是监督矩阵按标签集合算 Jaccard，自定义标签在语料里不存在，与任何样本的相似度都是 0，加进去等于噪声。后端 `normalize()` 会过滤掉非标准标签。

### 17.3 实现

新增 `backend/app/services/label_service.py`。

大模型路径：把 19 个类别写进提示词，要求只输出 JSON 数组，`temperature=0.1`。解析时用正则抠出数组，再逐个校验是否在标签空间内。

规则路径：大模型不可用或返回空时，退回 `extract_themes` 词典抽取；仍为空则返回空建议，由人工选择。

接口三个：

`GET /api/admin/review/labels` 返回标签空间与上限

`POST /api/admin/review/tags` 手动设置，传空数组表示保持无标签

`POST /api/admin/review/suggest-tags` 生成建议，不落库，由人工确认后保存

审核页在摘要下方展示标签徽章和"标注"入口，弹窗内可多选类别、点"AI 建议"自动填充、保存后即时刷新。

### 17.4 踩到的坑

项目用的模型是推理型，`max_tokens=200` 时预算全被 `reasoning_content` 消耗，`content` 返回空串，`finish_reason=length`。表现为"AI 建议"时好时坏，同一句话两次结果不同。

处理：`max_tokens` 提到 1200，并在 `content` 为空时从 `reasoning_content` 尾部兜底取内容。实测三条文本耗时 1.5 到 2.7 秒，标签准确。

### 17.5 与训练的关系

标签只在训练时构造监督矩阵。给一条记录打标签后，它会在下一次该窗口重训时进入监督项；同时窗口覆盖率上升，表权重随之提高。

给记录清空标签不会立即改变已有模型的参数，只影响下一次重训。

### 17.6 验证

`backend/tests/test_labeling.py` 覆盖解析过滤、人工标签收敛、写回索引、空文本建议。连同先前用例共 21 条，全部通过。

## 十八、全量图像库（图像搜图像）

### 18.1 定位

主索引里的图像是按情绪弱配对挂到文本语音记录上的 1686 张，服务跨模态检索。这里新增一条独立通道，覆盖 FER2013 全部 35887 张，只做图像搜图像，不参与跨模态配对训练，也不影响原有链路。

### 18.2 实现

数据侧：`scripts/build_image_corpus.py` 抽取全量特征写入 `image_corpus.db`，35887 张耗时 50 秒，文件 37MB。特征是 192 维手工描述子，与主索引一致。特征以 float32 二进制存 BLOB，比 JSON 省一半体积。

模型侧：`app/engines/hashing/image_index.py`。不用 CMFH，因为它的 G 是 n×n 稠密矩阵，35887 条要 10GB 内存。改用 PCA 降维到 64 维加 ITQ 迭代旋转，纯 numpy 实现，首次训练 0.9 秒，之后读缓存。

索引侧：复用 `MultiTableHashIndex`，单窗口，8 位带。

接口侧：前端不加任何开关。检索页上传图像时默认把"检索范围"设为「仅图像线索」，后端据此路由：查询模态为图像且范围为「仅图像线索」时走全量图像库；范围为「全部模态」时仍走主引擎做跨模态；文字与语音查询不变。`corpus=image` 参数保留为显式覆盖入口。

| 查询方式 | 检索范围 | 走哪条路 |
| --- | --- | --- |
| 上传图像 | 仅图像线索 | 全量图像库 35887 张 |
| 上传图像 | 全部模态 | 主引擎（跨模态，图搜文/图搜语音） |
| 文字 / 语音 | 任意 | 主引擎（跨模态） |

### 18.3 实测精度

测试集 1000 张作查询，top-10 同类表情比例 **0.2018**，随机基线 0.173。提升约 3 个百分点。

分层均衡采样下（每类 600 张）做了特征对照，随机基线 0.143：

| 特征 | top-10 同类率 |
| --- | --- |
| 原始 192 维 | 0.151 |
| HOG 900 维 | 0.156 |
| 两者拼接 1092 维 | 0.165 |
| LDA 有监督降维 6 维 | 0.158 |

四种方案全部贴着随机线。这说明瓶颈不在哈希，也不在降维方式，而在于 192 维手工描述子和 HOG 都没能提取到表情信息。

FER2013 是 48×48 的野外灰度人脸，表情差异集中在嘴角、眼角等细微结构，灰度均值、梯度直方图这类统计量抓不住。同类不同人的差异远大于同人不同表情的差异。

### 18.4 结论与选项

功能可用，链路完整，但精度不具备实用价值。三个选择：

一，维持现状，定位为链路验证，文档与答辩中如实说明精度接近随机。

二，引入 CNN 特征。MobileNetV2 ONNX 约 14MB，onnxruntime 约 15MB，35887 张 CPU 推理约 3 分钟，同类率可到 0.6 以上。当前环境未安装任何深度学习依赖，需要新装约 30MB 包，并解决模型文件下载。

三，放弃图像搜图像，只保留跨模态弱配对。

选二的话，`ImageHashIndex` 的特征抽取函数可替换，其余代码不动。
