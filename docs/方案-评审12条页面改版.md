## 二、还没改完的 4 处，具体怎么改

### A. 意见 8 的漏做：首页三个入口会停在错的页签

**问题**（不是设计问题，是 bug）：三个 hero 入口的链接都是 `personal-collect.html`
（`personal-home.html:45 / 54 / 63`），而采集页的页签脚本只认 `#text` 和 `#image`，
**语音是默认页**（`personal-collect.html:339-340`）。结果：

| 点这个入口 | 实际停在 |
|---|---|
| 写一段话 | 语音片段 ❌ |
| 录一段语音 | 语音片段 ✅（碰巧） |
| 上传一张图 | 语音片段 ❌ |

**改法**（两行）：

1. `personal-home.html:45 / 54 / 63` 三个 `href` 分别改成 `personal-collect.html#text`、`#audio`、`#image`；
2. `personal-collect.html:340` 的判断补上 `audio`：
   `if (hash === 'text' || hash === 'audio' || hash === 'image') select(hash);`

**验收**：三个入口分别点进去，页签与入口文案一致；深色模式同样；从"我的档案/预警中心"
跳回采集页时也带对应 hash。

### B. 意见 10：预警卡里的方框（去 AI 味）

**诊断**：AI 味不在"有方框"，而在于**卡片里再套方框**——外层是带描边的 `alertcard`，
里层又套一个浅蓝底 + 蓝左边框 + 圆角的 `.note--care`，而且红/橙两条各套一次。
最该被看到的"现在可以做的一件事"（危机第一响应）反而被做成了最像模板的一块。

**范围可控**：全站带**底纹**的方框只有 4 处，其余 `.note` 都是无底纹的（`base.css:664-700`）：

| 位置 | 内容 | 处理 |
|---|---|---|
| `personal-alerts.html:102-111` | 红色预警「现在可以做的一件事」 | **改**（被点名） |
| `personal-alerts.html:132-137` | 橙色预警「系统建议」 | **改**（去掉容器） |
| `personal-rag.html:175-186` | 报告末尾「出现以下情况请立即联系支持资源」 | 保留内容，换形态 |
| `personal-screening.html:133-142` | 第 9 题答完后的支持信息 | 保留内容，换形态 |
| `personal-profile.html:218-222` | 「完整建议见 RAG 分析结果」 | 降级成一行普通链接文案 |

**改法（推荐）**

1. **红色卡**：把方框换成**行动清单**——与首页「今天先做这些」同款的可勾选条目
   （复用 `.homex-plan` 组件），最后一条是危机资源：
   `热线 12356（24 小时）· 有立即危险拨打 120`，号码用 `.mono`。
   同时把热线从段落中间提出来，做进卡片底部动作条（与「联系咨询师」同一行），
   因为它是这一屏最该被点到的元素。
2. **橙色卡**：「系统建议」不套容器，改成正文后面接一句——
   `<b>建议</b>　进行 10 分钟呼吸训练，并把学习任务拆成 25 分钟的番茄钟。`（引导词加粗，正文照排）。
3. **黄色卡**：本来就没有方框（已核对 `:146-170`），不动。
4. **`.note--care` 这个类**：从"蓝底 + 蓝边 + 圆角方框"改成**无底色、无描边、无彩条**，
   只保留标题字重与行距差；留给全站仅有的两处真正的危机提示（screening 第 9 题、rag 报告末尾）。
   理由：彩色左边框正是意见 12 批评的同一种笔迹，不能一边改管理端一边在个人端继续用。
5. **写进约定**（`prototype/HANDOFF.md` 第四节）：**一张卡里最多一块带底纹的强调区**；
   层级用字重、字号、留白和 hairline 分隔线表达，不用"再加一层容器"。

**验收**：预警中心三张卡在浅色/深色下都不再有嵌套方框；红色卡的行动项可勾选；
热线号码在一屏内可见且可点。

### C. 意见 11：我的档案的「筛查记录」整张表都是量表

**诊断**：这是"量表中心"的残留，和首页已经改好的口径**自相矛盾**——
首页写着"量表只作辅助"，档案页却把量表当主语，连筛选器都只按 PHQ-9 / GAD-7 / ISI / PSS-10 分。
评委顺着演示动线从首页走到档案页，会立刻看出两页不是一个逻辑。

**改法**

1. **主表换成多模态记录**：列改为
   `编号 | 来源（文本·语音·图像）| 综合状态 | 等级 | 关联预警 | 日期`，
   数据与首页"当前综合状态"同源（`51 / 100` 这类值）。
2. **量表记录降级**：作为同一张卡里的第二个页签（或折叠区）「量表对照 · 4 条」，
   表头保留原来的"得分 / 满分 / 等级"，并继续用 `15 / 27 分` 的写法（这是意见 1/3 的共识写法）。
   **不建议把量表彻底删掉**：4 份量表是项目真实存在的组成部分，也是后端 `questionnaires`
   表里唯一的真实业务数据，删了就少一个可讲点。
3. **筛选 chips** 从四份量表改成 `全部 / 需关注 / 稳定`（或 `全部模态 / 文本 / 语音 / 图像`）。
4. 表格底部按钮「继续未完成的量表」→「继续未完成的记录」。

**验收**：默认打开档案页，第一眼看到的是多模态记录；量表要主动切页签才看得到；
两页对"什么是重点"的表述一致。

### D. 意见 12：管理端案例卡的边框

**诊断**：六张**等权重卡片**、每张一条 **3px 彩色左边框**、加上表格页同款的圆角描边——
这是生成式后台最典型的笔迹。而且"案例管理"这个页面的核心动作是**排序与分派**，
卡片墙承载不了它。另一个隐性问题是信息密度低：`.casecard` 只渲染了姓名/编号/院系/筛查次数/状态，
而数据里的 `年龄 / 性别 / 标签 / 最近筛查` 有值却没用上（标签还专门做了"标签聚类"侧栏，正文却不显示）。

**改法（两个档位）**

- **最小改动**：去掉每张卡的彩色左边框，等级只用卡内一枚状态点 + 文字（已有的 `pill`）；
  卡片之间改用 hairline 分隔或收窄圆角；**不动**全局 `.card`（管理端 8 个页面共用）。
- **推荐做法：左列表 + 右详情（主从布局）**
  - 左列：一行一个案例——`姓名 + 编号 · 等级点 · 最近筛查 · 当前状态 · 标签（前 2 个）`，
    点一行选中；
  - 右侧：被选中对象的详情（标签、筛查次数、最近筛查、关联预警、随访记录、操作按钮），
    现有侧栏的"标签聚类 / 本周待办"可以并进详情或保留在页面级；
  - 好处：与「预警管理」的表格风格统一，一眼看出"先处理谁"，顺带把没用上的字段用起来，
    而且**不需要新增数据**——`CaseRecord` 字段都是现成的。

**验收**：管理端案例页在浅色/深色下不再有彩色左边框；一屏内能看出全部 6 个案例的等级排序；
点选后详情可操作。

> React 侧注意：React 的 `ui-card`（`frontend/src/index.css:218-224`，24px 圆角 + 大投影）
> 被 **23 个文件、其中 8 个管理页**共用，**不要全局改**；只在案例页换用轻量类，
> 仓库里已有参考写法：`DashboardV2.tsx:279`。

## 三、会被评委当场问到的三件事（建议排在 UI 之前处理）

### 1. 图像 / 语音上传目前出的是**无意义结果**（已实测复核）

- 当前检索语料是**合成语料** `backend/data/hashing/corpus.db`（`real_corpus.db` 不存在），
  其中标着 `image` / `audio` 的 900 个单元，内容其实是**文字描述**
  （例如 `image` 单元内容是"画面中呈现：频繁看时间、坐姿前倾…"）。
- 因此三张投影矩阵 `W[text] / W[image] / W[audio]` **都是 64×275**（本次已复核
  `backend/data/hashing/hashing_state.json`）。
- 真实图像查询是 192 维、语音是 64 维，进不了 275 维的投影矩阵，被跳过 →
  `encode_continuous` 返回全 0 → 二值化后变成**全 1 码**（`cmfh.py:114-121`）。
  结果是：图像/语音上传的相似度退化成固定值，**与上传内容无关**；同一引擎下文本查询正常。
- 也就是说：首页 hero 的"写一段话 / 录一段语音 / 上传一张图"，**只有"写一段话"是真的**。

**建议三步（按性价比排序）**

| 步骤 | 做什么 | 成本 | 效果 |
|---|---|---|---|
| ① 立刻 | 维度不匹配时**显式返回"该模态暂不支持/证据不足"**，而不是静默降级成全 1 码 | 1 小时 | 不再输出"看起来正常但无意义"的分数——与项目一贯的"诚实优先"一致 |
| ② 演示层 | 三模态入口保留，但每路如实标注：文本＝真实链路，图像/语音＝演示样本；演示动线里只用文本做真链路 | 半天 | 评委点什么都不会翻车 |
| ③ 治本 | 用 `backend/scripts/build_real_corpus.py` 构建真实语料（EATD / CSEMOTIONS / FER2013）并重训状态 | 需要数据集，1–2 天 | 图像 192 维、语音 64 维才有对应的投影矩阵，"多模态"才立得住 |

> 这一条不是 UI 问题，但它决定 UI 能不能这么承诺。**建议答辩前至少做到 ① 和 ②。**

### 2. 「问问分析助手」在原型里不接模型

现状：`personal-home.html:384-394` 的脚本只把快捷问题**填进输入框**，点了不会有任何回答。
评委一定会点。两个选项：

- **(推荐) 本地预置问答**：4 个快捷问题各配一段带出处的回答，点击就地展开，
  明确标注"演示数据"。既不撒谎，又能把 RAG 的"结论 / 依据 / 建议"结构演示出来。
- 或明确标注"接口未接通"并禁用（与项目既有的诚实约定一致，但不好看）。

后端现状供参考：有 LLM 调用封装（`engines/rag/deepseek_rag_engine.py:188`）和降级策略，
但**没有会话/多轮/流式**，`ENABLE_MOCK_ENGINES=True`（`engines/__init__.py:11`），
治理开关 `AGENT_ALLOW_EXTERNAL_LLM=False`（`config.py:49`），知识库只有 6 条硬编码。
真要做对话助手，先把"单轮问答 + 证据包做上下文 + 危机词转介"做出来，不要一上来做多轮流式。

### 3. 三套东西已经分叉

| | 首页 | 导航 | 数据 |
